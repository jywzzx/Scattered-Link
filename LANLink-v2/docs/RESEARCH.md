# 调研报告：樱花穿透 / Radmin VPN 原理拆解与开源方案选型

> **结论先行**
> 1. 樱花穿透 = frp 反向隧道 + 托管中继；Radmin VPN = 二层虚拟网卡 + P2P 隧道。
>    两者路线完全相反：一个是"把端口搬到公网"，一个是"把你的电脑搬进同一个交换机"。
> 2. 满足「无需注册 + 不接第三方 SDK + 个人免费 + 有现成 Windows/Android 二进制」四个条件的
>    开源方案，只有 **EasyTier**（Apache-2.0）。
> 3. EasyTier 是三层（TUN），Radmin 是二层（TAP）。这决定了：**"ping 得通、能直连 IP"一定能做到，
>    "游戏列表里自动弹出房间"不保证**。本产品用"直接填虚拟 IP"绕开这个差异，并在文档里讲明白。

---

## 一、樱花穿透（SakuraFrp）的底层

内核是 **frp**（Fast Reverse Proxy，Apache-2.0，Go 写）。樱花做的只是"替你养了一台公网中继"。

```
① frpc(你的电脑) ──主动出向──> frps(公网中继:7000)     控制通道，长连接
② frpc 告诉 frps：隧道 X 绑到公网端口 30000
③ 朋友的游戏 ──> frps:30000                            frps 查表找到隧道 X
④ frps ──控制通道──> frpc                              "有人来了，开数据通道"
⑤ frpc ──主动出向──> frps                              第二条内向外连接
⑥ frps 搬运字节流 <-> frpc <-> 127.0.0.1:你的游戏端口
```

**它并没有"穿透"NAT，而是顺从 NAT 的单向性**：所有连接都由内向外发起，防火墙看到的是出站流量。

致命约束（正是本项目要绕开的）：

| 约束 | 后果 |
|---|---|
| 流量 100% 过中继 | 带宽 = 中继带宽（免费档 10Mbps / 月 5GiB） |
| 必须注册账号 | 要登录面板建隧道、拿 token |
| 服务暴露在公网端口 | 扫描器能扫到你的服务 |
| 只能"一对一端口" | 游戏里得手动填 `中继地址:30000`，**局域网发现完全失效** |

## 二、Radmin VPN 的底层（这才是用户想要的形态）

Radmin VPN（原 Radmin LAN）不是代理，是**虚拟交换机**。

```
┌────────────── 你的电脑 ───────────────┐
│  游戏 → 虚拟网卡(26.x.x.x) → 驱动封装  │
│        以太网帧 → UDP → 公网           │
└────────────────┬──────────────────────┘
                 │  P2P 直连（优先）
                 │  打洞失败 → 官方中继转发
┌────────────────┴──────────────────────┐
│  朋友的电脑 → 解包 → 注入虚拟网卡       │
│  游戏看到的"局域网"里就多了一台机器     │
└───────────────────────────────────────┘
```

四个关键设计：

1. **二层（L2）虚拟以太网适配器**，不是三层 TUN。
2. **封装的是以太网帧**（含广播帧、组播帧），不是 IP 包。
3. **广播/组播被原样转发** —— 这是"局域网自动发现"能工作的唯一原因。
   大多数游戏的 LAN 发现靠 UDP 广播（`255.255.255.255`）
   或组播（Minecraft 用 `224.0.0.60:4445`），这些包在 L3 隧道里通常到不了对端。
4. **STUN 打洞 + 中继兜底**，对称型 NAT 时自动降级。

**所以 Radmin 的体验才那么好**：装完 → 加入网络 → 游戏里"局域网"列表自动出现房间。

## 三、L2 与 L3 的取舍（本项目最重要的一次工程决策）

| | L2（Radmin / n2n / ZeroTier） | L3（EasyTier / Tailscale / WireGuard） |
|---|---|---|
| 虚拟网卡类型 | TAP（以太网） | TUN（IP） |
| 广播 / 组播 | ✅ 天然支持 | ⚠️ 有限，多数实现不转发组播 |
| 游戏自动发现 | ✅ 能弹房间 | ❌ 通常要手动填 IP |
| 实现复杂度 | 高（要自己做 ARP、MAC 表） | 中（交给内核路由） |
| 跨平台难度 | 高（Android 要 root 或特殊处理） | 低（VpnService 就是 TUN） |
| 现成可用二进制 | n2n 有，但需 supernode | EasyTier 有，且纯 P2P |

**我们的选择：L3 + 显式告诉用户对方的虚拟 IP。**

理由：
- Android 的 `VpnService` 给的是 **TUN**，做 L2 在非 root 设备上极其别扭；这直接决定 L2 方案在手机端会崩。
- 用"10.144.0.1"这种固定虚拟 IP，游戏里 90% 场景可以直接"添加服务器 → 填 IP"接上，
  体验损失远小于"手机端根本不能用"。
- 绝大多数现代联机游戏（Minecraft Java / 泰拉瑞亚 / 星露谷 / 帕鲁 / 方舟）都支持**直连 IP**。

诚实标注：**我们做到"同一个虚拟局域网、ping 得通、直连 IP 能进"，
不保证"游戏列表里自动出现房间"**。这是 L3 方案的物理上限，不是实现缺陷。

## 四、9 个开源方案横向对比

筛选条件（缺一不可）：
**① 免注册 ② 不接第三方 SDK ③ 个人使用免费 ④ 有官方 Windows 二进制 ⑤ 有 Android 客户端**

| 方案 | 许可 | 免注册 | 纯P2P | Win 现成包 | Android | 需驱动 | 结论 |
|---|---|---|---|---|---|---|---|
| **EasyTier** | Apache-2.0 | ✅ | ✅ | ✅ 31MB | ✅ 官方 APK | Wintun（自带） | ✅ **采用** |
| n2n | GPL-3 | ✅ | ⚠ 需 supernode 或 edge 互指 | ✅ | ⚠ 第三方 APK | TAP（装驱动） | supernode 门槛高 |
| ZeroTier | BSL-1.1 | ❌ 需 controller | ✅ | ✅ | ✅ | 是 | 许可非 OSI，需注册 |
| Tailscale | 闭源客户端 | ❌ | ✅ | ✅ | ✅ | 是 | 客户端不开源 |
| Headscale | BSD-3 | ✅ | ✅ | ⚠ 仍需 Tailscale 客户端 | ✅ | 是 | 客户端绕不开 |
| NetBird | BSD-3/AGPL | ✅ | ✅ | ✅ | ✅ | 是 | 要自建 mgmt+signal+relay |
| Nebula | MIT | ✅ | ✅ | ✅ | ⚠ 仅源码 | 是 | 要自建 CA + lighthouse |
| WireGuard | GPL-2 | ✅ | ❌ 需公网端 | ✅ | ✅ | 是 | 不解决打洞 |
| frp / 樱花 | Apache-2.0 | ✅/❌ | ❌ 需服务器 | ✅ | ❌ | 否 | 要公网服务器 |

**只有 EasyTier 同时满足五项**，而且它的核心正是"打洞 + 中继兜底"，与 Radmin 的网络层等价。

## 五、最终技术选型

```
┌───────────────────────────────┐
│  LANLink.exe（我们写的）       │  ← Swing 图形界面，小白只需点两下
│  · 生成/解析邀请码             │
│  · 探测本机公网 IP（STUN）      │
│  · 启动/停止内核 · 状态检测     │
└──────────┬────────────────────┘
           │  子进程（零代码修改）
┌──────────▼────────────────────┐
│  easytier-core.exe v2.6.4      │  ← Apache-2.0 原版，未改一行
│  · P2P 打洞 · 加密 · Wintun     │
└────────────────────────────────┘
```

- **"最小代码改动量"**：改动量为 **0 行**。我们只做参数生成与进程托管 —— 比"改开源代码"更小。
- **不做的事**：不自己实现打洞、不自己写虚拟网卡驱动、不造协调服务器。
- **邀请码**：`IP:PORT#密码`，房间名由密码 SHA-256 派生，所以"只输 IP + 念个密码"就能对上房间。

### 为什么不做自己的虚拟网卡

Windows 上创建 TUN 设备必须有内核驱动（Wintun / TAP-Windows），
调用它需要 C/C++ 或 JNI —— 本机没有 gcc/clang，也没有 NDK。
这是硬约束，也是选择"包一个成熟内核"而不是"自己写"的根本原因。
