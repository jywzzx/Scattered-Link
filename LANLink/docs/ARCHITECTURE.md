# 架构与协议说明

## 1. 进程模型

```
┌──────────────────────────────────────────────────────────┐
│  单个 Node 进程 (node src/main.js)                        │
│                                                          │
│  ┌────────────┐   HTTP/SSE   ┌───────────────────────┐   │
│  │ 浏览器 PWA │ <──────────> │  App (src/server.js)  │   │
│  │ PC / 手机  │              │  控制面 + 状态机       │   │
│  └────────────┘              └──────────┬────────────┘   │
│                                         │                │
│                              ┌──────────▼────────────┐   │
│                              │ Tunnel (src/tunnel.js)│   │
│                              │ UDP + 握手 + 多流复用  │   │
│                              └──────────┬────────────┘   │
│                                         │                │
│              ┌──────────────────────────┼──────────────┐ │
│              │                          │              │ │
│     ┌────────▼────────┐      ┌──────────▼─────────┐    │ │
│     │ReliableStream   │      │ bridge.js          │    │ │
│     │可靠有序字节流    │      │ TCP <-> Stream 泵   │    │ │
│     └─────────────────┘      └──────────┬─────────┘    │ │
│                                         │              │ │
└─────────────────────────────────────────┼──────────────┘ │
                                          │ TCP            │
                                   ┌──────▼──────┐         │
                                   │  游戏服务端  │         │
                                   └─────────────┘
```

- **主机模式**：`Tunnel(role=host)` 监听 UDP 端口 → 收到对端 SYN → 拨号本地 `127.0.0.1:游戏端口` → 双向桥接。
- **加入模式**：`Tunnel(role=guest)` 主动握手 → 本地监听 `127.0.0.1:同端口` → 每来一条 TCP 连接就开一条隧道流。

## 3. 线格式

所有隧道报文共用一个 14 字节头：

```
 0     type      u8     1=HELLO 2=HELLO_ACK 3=DATA 4=ACK 5=SYN 6=FIN 7=RST 8=PING 9=PONG
 1-2   streamId  u16BE  高 4 位 = peer 槽位(0..15)，低 12 位 = 流序号
 3-6   seq       u32BE  本端发送序号（包序号，非字节序号）
 7-10  ack       u32BE  本端期望收到的下一个序号
 11    flags     u8     预留
 12-13 length    u16BE  payload 长度
 14..  payload
```

单包 payload 上限 1100 字节 —— 刻意留出余量，避免 PPPoE / 隧道封装把 1500 MTU 撑爆导致分片。

## 4. 握手（3 步，天然抗重放）

```
guest                                              host
  │  HELLO: nonce_c(16) || HMAC(token,"lanlink-hello",nonce_c)[0..8]
  ├───────────────────────────────────────────────────>
  │                          HELLO_ACK: nonce_h(16) || HMAC(token,"lanlink-ack",nonce_c||nonce_h)[0..8]
  <───────────────────────────────────────────────────┤
  │  校验通过 → 建立会话（记下 rinfo 即为对端公网端点，顺带完成打洞）
```

- 令牌 4 字节随机，只存在于连接码里，不上传任何服务器。
- 用常量时间比较（`crypto.timingSafeEqual`）避免时序侧信道。
- 令牌错误时主机直接丢弃，不返回任何响应 —— 对外表现为"不可达"，不泄露主机存在。

## 5. 可靠流的最小实现

只做联机需要的事，明确**不做**拥塞控制（局域网/单用户场景下它只会拖慢速度）：

- **序号空间**：按"包"编号，不是按字节。省掉复杂的分段重组。
- **接收**：`recvNext` 期望序号，乱序包进 `recvMap` 暂存，缺口补上后连续吐出。
- **发送**：固定窗口 32 包（≈35 KB 在途），`sendQueue` 保存未确认包。
- **重传**：RTO 220ms 起，每次重传翻倍（上限 2s），单包 14 次失败即断流；
  外加「连续 3 个重复 ACK 立即快速重传」。
- **半关闭**：`end()` 只置标志，等发送队列排空才真正发 FIN；
  收 FIN 只关读方向，本端仍可继续发剩余数据。这与 TCP 语义一致，
  是"客户端发完就 end、还要等回声"这类游戏行为的必要条件。
- **优雅收尾**：双向都 FIN 后再等 400ms 才销毁，保证最后一帧 ACK 能落地。

## 6. 安全边界

| 面 | 措施 |
| --- | --- |
| 谁能连进来 | 必须持有 4 字节令牌（128-bit 熵的 HMAC 挑战应答） |
| 能访问哪个端口 | **白名单**：主机只转发自己指定的那一个 `servicePort`，其余一律 RST |
| 主机本地服务暴露范围 | `127.0.0.1`，不监听 `0.0.0.0`，链路上的朋友也够不到你别的服务 |
| 控制台谁能打开 | 只绑定 `127.0.0.1`，外部无法访问 UI/API |
| 路径穿越 | 静态资源做 `path.resolve` 前缀校验 |
| 请求体 | 上限 64 KB |
| XSS | 全部 DOM 写入走 `textContent`，不用 `innerHTML` 拼接用户数据 |

## 7. 已知边界（诚实列出）

1. **对称型 NAT + 无 IPv6 + UPnP 关闭** → 无法直连。程序会明确降级提示，不会假装成功。
2. **一个主机同时只能转发一种服务端口**（可扩展，当前刻意不做，避免过度设计）。
3. **不支持 UDP 转发**。Minecraft Java、泰拉瑞亚、星露谷、Rust、幻兽帕鲁等都是 TCP；
   基岩版走 UDP，当前版本不支持。
4. **局域网广播发现（LAN discovery）不跨越隧道**。需要在游戏里手动输入 `127.0.0.1`。
5. 无中继 → 双方网络都不支持直连时没有兜底。
