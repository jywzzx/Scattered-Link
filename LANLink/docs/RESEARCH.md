# 调研报告：樱花穿透原理 & 零成本远程局域网方案选型

> 结论先行：**没有任何方案能在"完全零注册、零第三方、零服务器"的前提下 100% 保证跨网直连**。
> 本项目的做法是把「IPv6 直连 → 路由器 UPnP 自动放行 → STUN 打洞」三条免费路径全部内置，
> 按可用性自动降级，并在界面上明确告诉用户当前走的是哪条路、为什么。

---

## 1. 樱花穿透（SakuraFrp）到底在做什么

### 1.1 它不是一个"协议"，是 frp 的托管服务

樱花穿透的内核是开源的 **[frp](https://github.com/fatedier/frp)**（Fast Reverse Proxy，Apache-2.0，Go 编写）。
官方在 frp 之上加了三样东西：公网中继节点集群、集中式管理面板、账号/流量/限速体系。
所以理解樱花 = 理解 frp + 理解托管服务替你做掉了哪一步。

### 1.2 frp 的核心：反向隧道

NAT 的本质约束是**单向的**：内网可以主动向外发起连接，外网不能主动向内发起。

frp 完全顺从这个约束，全程不"穿透"NAT：

```
① frpc(内网) ──主动出向──> frps(公网:7000)      建立持久控制通道
② frpc 通过控制通道告诉 frps：把我的隧道 X 绑到公网端口 P
③ 访客 ──> frps:P                                frps 查映射表，找到隧道 X
④ frps ──控制通道通知──> frpc：有人来了，开一条数据通道
⑤ frpc ──主动出向──> frps                       建立 work conn（第二条内向外连接）
⑥ frps 把访客的字节流搬进 work conn，frpc 收到后转发到 127.0.0.1:游戏端口
```

关键点：

- **TCP 隧道**：一条访客连接对应一条数据通道，双向 `io.Copy` 搬运，天然保序。
- **UDP 隧道**：frps 在公网端口收 UDP 包，按来源地址建会话表，把 UDP 报文封装进控制/数据通道
  传回 frpc，再把回包反向送回。本质是 **UDP over TCP**，所以延迟比原生 UDP 略高，
  但对 Minecraft 基岩版、泰拉瑞亚这类游戏完全够用。
- **HTTP/HTTPS 隧道**：靠 `Host` 头 / TLS SNI 在同一个 80/443 上分流，不需要额外端口。
- **为什么能成功**：所有连接都是「由内向外」发起的，NAT 表项是新建立的，防火墙看到的是
  出站流量，全部放行。frp 从头到尾没有触碰 NAT 的入站限制。

### 1.3 由此带来的固有限制（也是我们不选它的原因）

| 限制 | 说明 |
| --- | --- |
| 流量全部过中继 | 带宽 = 中继节点带宽；樱花免费档 10 Mbps / 每月 5 GiB |
| 强依赖中继可用性 | 节点挂了 = 服务挂了 |
| 需要注册账号 | 要登录面板建隧道、拿 token |
| 数据默认不过端到端加密 | frp 隧道明文，敏感服务需自行叠加 TLS |
| 隐私 | 你的内网服务暴露在第三方公网端口上，扫描器能扫到 |

这三条正好命中用户的硬性要求：**无需注册、不接第三方、个人免费**，所以必须换路线。

## 2. 候选开源方案横向对比

| 方案 | 类型 | 许可 | 需要注册 | 需要公网服务器 | 需要虚拟网卡/管理员 | 跨平台 | 结论 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| **frp** | 反向隧道 | Apache-2.0 | 否 | **是** | 否 | 全平台 | 要服务器，排除 |
| **EasyTier** | P2P Mesh VPN | Apache-2.0 | 否 | 可选（有公共节点/可自建） | **是**（TUN） | 全平台含 Android | 优秀，但需驱动 |
| **Headscale** | Tailscale 控制面 | BSD-3 | 否 | **是** | 是 | 用官方闭源客户端 | 客户端非纯开源，排除 |
| **NetBird** | Mesh VPN | BSD-3/AGPL | 否 | **是**（mgmt+signal+relay） | 是 | 全平台 | 组件重，排除 |
| **Nebula** | 证书 Overlay | MIT | 否 | 需 lighthouse + CA | 是 | 全平台 | 运维成本高 |
| **ZeroTier** | L2 Overlay | BSL-1.1 | 是（控制器） | 可选 | 是 | 全平台 | 非 OSI 开源，排除 |
| **n2n** | P2P VPN | GPL-3 | 否 | 需 supernode | 是 | 桌面为主 | 老、移动端弱 |
| **纯 WireGuard** | VPN | GPL-2 | 否 | **必须有公网端点** | 是 | 全平台 | 不解决打洞 |
| **本方案（LANLink）** | 端口级 P2P 隧道 | MIT | **否** | **否** | **否** | Node 18+ 全平台 | ✅ 采用 |

### 2.1 为什么不用 EasyTier（虽然它最像答案）

EasyTier 确实是目前最优雅的开源 Tailscale 替代品：Apache-2.0、无需注册、P2P 打洞、
全平台、还自带免费公共中继节点。但它有两个对本项目致命的成本：

1. **必须有虚拟网卡**。Windows 要装 Wintun 驱动、要管理员权限；Android 要用 VpnService
   写一个原生壳。这与"最小改动、不过度设计、双击即用"直接冲突。
2. **它是整网段 VPN**，而不是端口级转发。对于"只想联一把游戏"的场景，等于用大炮打蚊子，
   而且会把本机所有内网服务都暴露给对端。

### 2.2 本项目选择的技术路线：端口级 P2P 隧道

只在**应用层**搬运 TCP 字节流，不碰内核、不装驱动、不要管理员权限：

```
游戏A ──TCP──> 127.0.0.1:25565 (本机监听)
                      │
                 [LANLink 隧道]
                 TCP 拆包 → UDP 打包 → 打洞/直连 → 对端
                      │
游戏B <──TCP── 127.0.0.1:xxx (对端监听) ──> 主机 127.0.0.1:25565
```

代价是要自己实现"UDP 上的可靠有序流"（相当于一个迷你 TCP），
收益是**零驱动、零权限、零安装、可以只暴露一个端口**。

## 3. 三条"免费直连"路径，以及各自的真实前提

严格意义上的 P2P 直连只有三条路，本项目全部内置并自动择优：

### 路径 A：公网 IPv6 直连（最优）

- 前提：双方宽带都下发公网 IPv6（国内移动/电信/联通近年大面积支持），且光猫/路由未封 ICMPv6。
- 优点：无 NAT、无中继、延迟最低、带宽满速。
- 缺点：公司网/校园网通常没有 IPv6。

### 路径 B：路由器 UPnP / NAT-PMP 自动端口映射

- 前提：路由器开启了 UPnP（家用路由默认多数开启）。
- 做法：程序 SSDP 发现网关 → SOAP `AddPortMapping` 给自己开一个 UDP 端口 → 拿到的公网
  `IP:Port` 就是稳定入口，对端直接连。
- 优点：不依赖 NAT 类型，对称型 NAT 也能用。
- 缺点：部分光猫/企业路由关闭了 UPnP；CGNAT 环境下即使映射成功也没有公网 IP。

### 路径 C：STUN 打洞（兜底）

- 前提：NAT 为锥型（Full/Restricted/Port-Restricted Cone）。
- 做法：双方各自向 STUN 服务器查询自己的公网映射，交换后再互发 UDP 包打洞。
- 缺点：对称型 NAT（部分移动网络、企业网）打洞成功率很低。
- 缓解：主机侧持续发送保活包维持映射，客户端以 300ms 间隔重试握手（最多 25 次）。

### 如果三条都失败

说明处于 **CGNAT + 无 IPv6 + UPnP 关闭** 的三重困境。此时只剩"中继"这一条路，
而中继必然需要一个公网节点（= 要花钱或要注册），与本需求冲突。
程序会明确提示"当前仅支持同一 WiFi 下联机"，而不是假装成功。

> 这就是为什么报告开头说"没有 100% 保证"。任何声称能做到的产品，要么在中继，
> 要么在用第三方协调服务器，要么在骗你。

## 4. 选型结论

| 维度 | 决策 |
| --- | --- |
| 隧道内核 | 自研 UDP 可靠流（14 字节定长头 + 包级序号 + 累积 ACK + RTO 重传 + 固定窗口） |
| 依赖 | **零第三方依赖**，只用 Node 内置 `dgram` / `net` / `http` / `crypto` |
| 注册 | 无账号、无云端、无遥测 |
| 公网发现 | STUN（标准协议，可一键关闭）+ UPnP（本地协议） |
| 鉴权 | 4 字节随机令牌 + HMAC-SHA256 握手，连接码内含 CRC8 校验 |
| 端口暴露 | 白名单，只转发用户指定的那一个端口 |
| 客户端形态 | 单进程本地 Web 服务 + PWA，PC/手机同一套界面 |
