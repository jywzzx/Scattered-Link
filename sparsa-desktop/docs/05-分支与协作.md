# 分支与协作方案

## 一、结论：已具备条件

仓库现状（2026-10-28 实测）：

| 项 | 值 |
|---|---|
| 仓库 | `jywzzx/Sparsa`（公开，原名 Scattered-Link，已更名） |
| 默认分支 | `main` |
| 分支数 | 1 |
| 提交数 | 7 |
| 分支保护 | 未开启 |
| token 权限 | admin / push 均有 |
| 源码 | 已入库，两端源码与文档均在版本控制下 |

**源码已入库**，分支开发不需要再做前置准备。当前只有 `main` 一条线，
后续按下面的命名与合并规则开短分支即可。

尚未做的两件事：

1. `main` 未开保护，仍可直接推送；
2. 发布脚本 `publish.py` 仍用 contents API 直接写 `main`，开保护后会被拒。

其余流程见后文。

## 二、推荐的协作模型

单人项目不要把流程做重。轻量三档：

### 分支命名

| 前缀 | 用途 | 例 |
|---|---|---|
| `feat/` | 新功能 | `feat/vue-phone-config` |
| `fix/` | 修缺陷 | `fix/relay-divergence` |
| `refactor/` | 不改行为的重构 | `refactor/engine-api` |
| `docs/` | 文档 | `docs/branch-flow` |
| `chore/` | 构建、依赖、版本号 | `chore/bump-2.7.0` |
| `release/` | 发布前收口 | `release/v2.7.0` |

规则：小写、连字符、≤ 40 字符、一个分支只做一件事。

### 合并方式：**Squash merge**

理由：
- `main` 历史保持一条线，`git log --oneline` 就是一份变更清单；
- 单人开发时分支内的「改错再改回」提交没有保留价值；
- 回滚粒度天然等于一个功能。

`rebase merge` 也线性，但会把中间过程提交全部塞进 `main`；`merge commit` 在单人项目里只会制造噪音。

### 生命周期

```
main ──●───────────────●───────────────●──→
        \             / \             /
         ●──●──●─────●   ●──●────────●
        feat/a (squash)   fix/b (squash)
```

- 分支存活 1–3 天，合并后立即删除
- 发布时从 `main` 打 tag（`v2.7.0`），**Release 只从 tag 构建**，
  保证「下载的包 ↔ 源码快照」能对上
- `main` 保护：禁止直推、要求 PR、要求构建检查通过（单人可自己 approve）

## 三、落地需要改哪些代码（改动量很小）

| 项 | 文件 | 改动量 |
|---|---|---|
| 源码入库 | 新增根 `.gitignore` | ~30 行 |
| 排除大文件 | 忽略 `engine/`、`release/`、`node_modules/`、`dist/`、`build/classes` | 同上 |
| 发布脚本适配 | `LANLink-v2/build/publish.py` | 把硬编码 `'main'` 提为 `--branch`；约 20 行 |
| | `LANLink-v2/build/publish-26x.py` | 同上；约 10 行 |
| 首次入库提交 | 约 50 个源文件（Java 17 + 前端 30+） | 一次性 |
| 构建检查 | 新增 `.github/workflows/ci.yml` | ~40 行 |
| 流程说明 | `CONTRIBUTING.md` | ~60 行 |

**合计约 150 行新增/改动**，没有架构性改动。原因是现有脚本已经把「仓库操作」
全部集中在 `gh_client.py` 一层，分支只是参数。

需要注意一处冲突：`publish.py` 现在用 contents API **直接写 `main`**
（写 README / LICENSE）。开启分支保护后这条会被拒。改法二选一：

- 简单：文档改动也走 PR，`publish.py` 只负责 Releases；
- 省事：只保护 `main` 的强制推送，允许管理员直推（单人项目可接受）。

## 四、后续维护：`main` 的改动主要落在哪

按当前代码形态估算（百分比为经验值，随迭代会漂移）：

| 区域 | 占比 | 具体文件 | 变动原因 |
|---|---|---|---|
| 前端页面 | ~30% | `sparsa-desktop/src/views/*`、`components/*` | 交互与文案迭代最快 |
| 内核参数与配置 | ~20% | `LANLink-v2/core/Engine.java`、`PhoneProfile.java` | 打洞/中继/NAT 兼容性反复调 |
| 接口层 | ~15% | `server/ApiServer.java`、`src/api/*` | 前后端契约演进 |
| 构建与发布 | ~15% | `build/*.py`、`build.ps1`、`package.py` | 每次版本号 + 打包逻辑 |
| 文档 | ~10% | `README.md`、`docs/*`、`使用说明.txt`、`待办清单.txt` | 与代码同步 |
| 测试 | ~10% | `src/test/java/lanlink/*`、`scripts/verify.mjs` | 随功能补断言 |

几个可以预期的热点：

- **`Engine.java` 与 `PhoneProfile.java`** 是历史 bug 最集中的两处（模式不一致、
  节点不通、配置不跟随），后续维护改动大概率仍在这里；
- **`views/PhoneView.vue`** 承接了手机端配置的全部逻辑，是前端最易回归的页面；
- **`build/package.py` 的 `VERSION`** 曾出现与 `build.ps1` 不同步导致产物名错版本，
  建议把版本号收敛到一个文件（前端 `package.json` + 后端单一常量）。

## 五、建议的执行顺序

1. 加 `.gitignore`，把两端 `src` 先入库（不含 `engine/`、`release/`、`node_modules/`）
2. 打 tag `v2.6.3` 对齐已发布的包，让历史有锚点
3. 开启 `main` 保护（禁直推 + 要求 PR）
4. 把 `publish.py` 的 `main` 提为参数，Release 改为从 tag 触发
5. 加 CI：`npm run verify` + `javac` 编译 + `lanlink.Tests`
