# UI 文案规范（硬性约束）

> 适用范围：`sparsa-desktop/src/**` 中一切用户可见文字 —— 标题、按钮、标签、占位符、提示、报错、空状态、确认框、Toast、悬浮说明、帮助文本、界面内嵌文档。
>
> 约束级别：**硬性**。不符合即视为缺陷，与功能 bug 同等对待。
> 本文件是后续重写前端时的唯一文案依据；新增文案前先读，评审时逐条对照。

## 一、六条不可突破的底线

1. **不许出现有意误导或夸大功能效果、隐瞒限制的表述。** 若功能有边界、风险或用户可能误解之处，必须明确说明限制或结论。
2. **任何文案不得含歧义或前后矛盾、表意不清晰。**
3. **不要为了显得热情而堆砌无关内容。**
4. **不采用口语化、学术化或翻译腔表述**，不得出现生硬直译，例如「当……时，会……」「通过……来……」。
5. **不得使用指代不明的人称代词**，例如「我们会……」，必须写明「本设备 / 本程序 / 用户」。
6. 面向普通用户的文案**以告知信息与指引操作为主**，描述与解释性内容应尽量简练；面向开发者或专业用户的文案**以说明机制、边界情况与潜在风险为主**。

## 二、翻译腔的典型表现（必须改写）

- 不要出现「请」「您」的敬语叠加，也不要每句都加「请」来软化语气。
- 不要使用被动语态堆叠：「被检测到」「被认为是」。
- 不要用「进行 / 作出」+ 名词的动宾拆分：「进行连接」「作出选择」。
- 不要滥用「对于 / 关于 / 针对」开头的长状语。
- 不要出现「动词名词化」：「配置的生成」→「生成配置」。
- 不要用「是否」做委婉疑问的填充：「检查是否成功」→「检查结果」。

## 三、句长与标点

| 要求 | 说明 |
|---|---|
| 中文句子长度不超过 35 个汉字 | 超长句必须拆分为短句，或改为列表 |
| 单条提示不超过 3 行 | 超过 3 行应改为结构化的多段或列表 |
| 不允许出现破折号 | 不得用 `——` 做插入说明 |
| 不允许使用分号 | 用句号或列表替代 |
| 不允许使用括号补充说明 | 括号只用于单位、IPv4 地址、文件名等非解释性内容 |
| 不允许用省略号制造语气 | 包括「加载中…」「等待接入…」，以及用 `…` 省略功能词 |

## 四、写作要求（按用途分组）

### 1. 语法、语气与结构
1. **名称与术语全篇统一**，同一功能、按钮、状态在不同页面使用同一名称。
2. **同一段落内避免句式重复**，句式不得连续造成工整感。
3. **中文与英文数字之间增加空格**，例如「10 秒」「v2.6.4」。IPv4 地址、邀请码等原样呈现，不加空格。
4. 界面整体以**短句和行动导向措辞**为主，直接说明「做什么」与「会得到什么结果」。
5. 按钮文案必须使用**动宾短语（动词 + 名词）**，如「创建房间」「复制配置内容」「断开连接」。不得只用名词或形容词，也不得使用「点击这里」「更多」。
6. **品牌层的短句可以简洁有力，但不允许使用对仗、比喻或商业口号**。标语和产品名归品牌层，功能提示一律平实表述。
7. 面向普通用户的产品，**不使用专业术语**；必须使用时，应在首次出现处用一句话解释，解释后统一用该术语。

### 2. 面向普通用户（界面提示、报错、帮助文档）
1. 不出现技术术语（如 TLS、UDP 打洞、NAT 穿透等），或先用通俗说法替代，再在帮助文档中说明。
2. 若必须保留专业名词（例如设备已有名称、系统组件名称），应给出**用户可理解的场景说明**，例如「虚拟网卡：创建后本机会多出一个网络适配器」。
3. 不引导用户采用外部产品、外部文档或其他平台的术语。第三方产品名称只在必须点名时出现，并说明用途与限制。

### 3. 面向专业用户与开发者（配置说明、诊断、接口文档、错误代码）
1. **允许使用准确的专业术语**，但术语必须与**真实实现一致**，可以追溯（能对应到实际参数、日志字段或接口字段）。
2. 说明机制时，同时说明**边界、前置条件与失败表现**。禁止只讲「能做什么」而不讲「什么情况下不成立」。
3. 涉及参数、端口、路径、版本时，必须写明取值范围或示例，不得用「适当」「合理」「若干」等模糊表述。
4. 风险提示必须写明**触发条件 + 后果 + 处理方式**，不得只写「注意」或「请谨慎操作」。
5. 错误提示不得只给结论，应包含**可执行的下一步**。

### 4. 按钮、提示、报错、空状态、确认框、Toast
1. **按钮**：动宾结构，动词在前，不超过 6 个汉字。
2. **提示**：描述当前状态与可执行动作，不描述系统内部实现。
3. **报错**：三段式 —— 发生了什么 / 为什么 / 用户接下来做什么。不出现异常堆栈、类名、方法名。
4. **空状态**：说明「当前没有数据」+「数据出现的条件」+「用户可执行的动作」。
5. **确认框**：标题说明操作对象，正文说明后果，按钮说明动作结果（如「断开」「保留连接」）。
6. **Toast**：只反馈结果，不承载说明；说明类内容应放在页面内。

### 5. 结构顺序
1. **现象 / 需求 → 原因 / 机制 → 处理方式 / 下一步。** 不得只给现象而不给处理方式。（面向普通用户时，「原因」可省略，但「下一步」不能省。）
2. **先结论后细节。**
3. **禁止「并非……而是……」句式。**
4. **禁止排比、对仗、比喻、拟人、反问、设问、感叹、口号、未来承诺**，以及「诗与远方」式文艺表达。
5. **不得使用「让我们一起」「快来」「千万不要错过」等营销或煽动性语气。**
6. 段落之间优先使用空行分隔，少用列表与编号；仅在并列项数量 ≥ 3 且同类时才用列表。
7. 同一字段在不同位置的描述必须一致（名称、单位、精度、取值范围）。

## 五、文案输出格式

需要给出文案时，按「位置 / 文案 / 包含的信息要素」三栏输出。示例：

| 位置 | 文案 | 包含的信息要素 |
|---|---|---|
| 创建房间页 · 主按钮 | 创建房间 | 动作 |
| 建房失败提示 | 内核启动后立即退出，虚拟网卡未能创建。请以管理员身份重新运行本程序。 | 现象 + 原因 + 下一步 |
| 成员列表 · 空状态 | 暂无成员接入。对方粘贴邀请码后，其虚拟 IP 会显示在这里。 | 现状 + 条件 + 结果 |

### 4. 自动化守卫

`npm run verify` 新增三条断言，防止回流：

1. 界面文案不含省略号、分号、破折号（跳过注释与正则定义）；
2. 不得出现中文口号「散落的设备」；
3. 英文短句必须保留。

断言命中会直接失败并给出文件与行号。
